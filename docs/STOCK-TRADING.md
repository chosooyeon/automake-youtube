## 1. 백테스트 엔진이 뭐 하는 건가

한 줄로: **"이 규칙대로 과거 3년간 매매했다면 지금 잔고가 얼마인가"를 계산한다.**

기존 `signals.ts`(알림 엔진)와 뭐가 다른가:

| | 알림 엔진 (`signals.ts`) | 백테스트 엔진 (`backtest.ts`) |
|---|---|---|
| 답하는 질문 | "지금 사야 할 것 같은가?" | "이렇게 사고팔았으면 벌었나?" |
| 청산 규칙 | 없음 | 손절·익절·보유기간 |
| 매매 크기 | 없음 | 리스크 기반 수량 계산 |
| 거래비용 | 없음 | 수수료·세금·슬리피지 차감 |
| 결과 | 신호 목록 | 수익률·MDD·승률·기댓값 |

신호가 좋아 보이는 것과 돈을 버는 것은 별개다. 그 차이가 청산·수량·비용에서 갈리는데,
알림 엔진에는 그 셋이 전부 없다. 그래서 알림만 보고는 이 전략이 돈을 버는지 알 수 없었다.

### 어떻게 돌아가나 (하루씩 시뮬레이션)

```
매 거래일마다:
  1) 보유 중인 종목 청산 판정   ← 오늘 봉의 고가/저가로 손절·익절 도달 확인
  2) 킬스위치 확인              ← 오늘 손실이 한도 넘으면 신규 진입 중단
  3) 신규 진입 판정             ← 어제 종가까지의 신호로 오늘 시가에 매수
  4) 잔고 기록                  ← 자산 곡선 한 점
```

### 이 엔진이 지키는 원칙: 미래를 보지 않는다

백테스트가 거짓말하는 가장 흔한 이유는 **미래 참조(lookahead)** 다.
"오늘 종가를 보고 오늘 종가에 산다"고 계산하면 백테스트는 천재가 되지만 실전에선 불가능하다.

이 엔진의 규칙:
- 신호는 **어제 종가까지**의 데이터로만 계산 (`analyze(candles.slice(0, i))`)
- 주문은 **오늘 시가**에 체결 — 실제로 낼 수 있는 주문만 낸다
- 한 봉에서 손절과 익절에 모두 닿았으면 **손절 먼저** 맞은 것으로 처리 (일봉으로는 순서를 알 수 없으므로 불리한 쪽)
- 갭하락으로 시가가 손절선 아래면 손절가가 아니라 **시가**에 체결 (실전과 동일)
- 진입 당일 장중 손절도 체크 (산 날은 안 잘린다는 가정 제거)

### 알려진 한계

- **일봉 기준**이라 장중 순서를 모른다. 분봉 전략은 이 엔진으로 검증 못 한다.
- **상장폐지·거래정지 종목이 빠져 있다** (생존 편향). 지금 관심종목에 살아있는 종목만 돌리므로 실제보다 유리하게 나온다.
- **배당·액면분할**이 네이버 데이터에 어떻게 반영되는지 검증하지 않았다.
- 슬리피지는 고정 bp로 근사한다. 거래량이 적은 종목은 실제로 더 밀린다.

## 3. 결과 읽는 기준 — 5개 다 통과해야 다음 단계

리포트 맨 아래 `[판정]` 이 이 표를 자동으로 채점한다.

| 항목 | 합격선 | 왜 이 기준인가 |
|---|---|---|
| **표본 수** | 거래 100회 이상 | 30회짜리 +50%는 운이다. 표본이 적으면 어떤 숫자도 의미 없다 |
| **기대값** | +0.1R 이상 | 1회 매매당 평균 손익을 손절폭(1R) 단위로 잰 값. **음수면 매매할수록 잃는다** |
| **Profit Factor** | 1.3 이상 | 총이익÷총손실. 1.0 = 본전. 비용·슬리피지 오차를 감안해 1.3을 최소선으로 둔다 |
| **MDD** | 25% 이내 | 고점 대비 최대 낙폭. **CAGR보다 중요하다** — 이걸 못 견디면 바닥에서 전략을 꺼버리게 된다 |
| **단순보유 대비** | 초과수익 | 그냥 사서 묻어둔 것보다 못하면 자동매매를 만들 이유가 없다 |

### 보조 지표

- **승률**: 단독으로는 무의미하다. 승률 35%에 손익비 3:1이면 훌륭하고, 승률 70%에 손익비 0.3:1이면 파산한다.
- **샤프**: 1.0 넘으면 양호. 다만 표본이 적으면 쉽게 뻥튀기된다.
- **비용 비중**: 손익 대비 수수료+세금 비율. 20%를 넘으면 매매가 너무 잦다는 뜻이다.

### 수익률은 어떻게 결정되는가

목표 수익률을 **정하는 게 아니라 계산되어 나온다**:

```
1회 기대손익 = 승률 × 평균수익 − 패율 × 평균손실     … 단위: R
연 수익률   ≈ 1회 기대손익(R) × 연간 매매횟수 × 1회 리스크(%)
```

예) 기대값 0.4R · 연 50회 매매 · 1회 리스크 1%
→ 0.4 × 50 × 1% = **연 20%** (비용 차감 후, 복리 효과 제외한 근사)

여기서 조절할 수 있는 손잡이는 세 개뿐이다:
1. **기대값을 올린다** — 규칙 개선. 가장 어렵고 가장 정직한 길
2. **매매 횟수를 늘린다** — 종목 수를 늘린다. 비용도 같이 늘어난다
3. **1회 리스크를 키운다** — 수익도 MDD도 같은 배수로 커진다. **공짜 없음**

3번이 유혹적이지만, 리스크를 2배로 하면 MDD도 2배가 된다.
연 40%를 노리면 MDD 50%를 각오해야 하고, 그 구간에서 전략을 지킬 수 있는 사람은 드물다.

### 현실적인 기대치

- 개인 시스템 트레이딩: **연 10~20% / MDD 20~30%** 면 성공한 축
- 월 5% 이상을 광고하는 백테스트는 십중팔구 과최적화이거나 미래 참조 버그
- 처음 몇 달은 **수익이 목표가 아니라 규칙을 지키는 것이 목표**다

## 4. 과최적화를 피하는 방법 (가장 중요)

설정을 이리저리 바꿔가며 수익률이 제일 높은 조합을 찾는 것 = **과거에 맞춰 깎기**.
그렇게 나온 숫자는 미래에 재현되지 않는다.

**반드시 이 순서로 한다:**

```bash
# ① 학습구간에서만 설정을 만진다
npx tsx ../scripts/backtest.ts --to 20250630

# ② 완성된 설정을 검증구간에 딱 한 번 돌린다
npx tsx ../scripts/backtest.ts --from 20250701
```

②의 성적이 ①과 비슷하면 쓸 만한 규칙이고, ②만 무너지면 과최적화다.
②를 보고 다시 설정을 고치면 검증구간도 학습구간이 되어버린다 — **딱 한 번만 본다.**

## 5. `config/stock-trading.json` — 내가 채워야 할 값

각 항목의 **현재 기본값**과 **정할 때 기준**이다.

### 파일은 2층이다 — 공통값 + 시장별 덮어쓰기

국내 설정을 그대로 미국에 들고 갔더니 PF 0.88 / -13.1% 로 **돈을 잃었다**(8-4).
그래서 시장마다 자기 규칙을 갖는다:

```json
{
  "entry": { "minNetScore": 4, ... },      // ← 공통 기본값 (적지 않은 시장이 물려받는다)
  "exit":  { "stopLossAtrMult": 2, ... },

  "markets": {
    "KR": { "label": "...", "note": "...", "verifiedAt": null },
    "US": { "label": "...", "note": "...", "verifiedAt": null,
            "exit": { "stopLossAtrMult": 3, "maxHoldDays": 40 },   // ← 이 시장만 덮어쓴다
            "costs": { "commissionBps": 7 } }
  }
}
```

`loadTradingConfig("US")` 가 두 층을 합쳐서 돌려주고, **백테스트·스윕·워크포워드가 전부
시장을 넘겨 받는다.** 인자를 안 주면 공통값만 나온다 — 시장이 정해지지 않은 자리에서
US 규칙이 새는 걸 막으려고 일부러 그렇게 뒀다.

화면에서는 admin **[📈 주식 매매] → [📐 방법론]** 이 두 시장 규칙을 나란히 보여준다
(다른 항목만 색으로 표시된다). 아래 항목별 설명은 공통값 기준이며, 시장별 실제 값은
그 화면이나 8-9 절의 표를 보면 된다.

> **`verifiedAt` 은 워크포워드를 통과한 날만 적는다.** null 이면 화면이 "⚠ 검증 전 (가설)" 로
> 표시한다. 스윕 표에서 제일 좋은 줄을 골라 여기 적는 건 4절이 경고한 과최적화다.

### capital — 총 투입 원금
```json
"capital": 3000000
```
기준: **전액 잃어도 생활에 지장 없는 금액.** 전체 자산이 아니다.
이 값이 크면 백테스트 수익률이 좋아 보이는 게 아니라 절대금액만 커진다 (수익률은 동일).

### entry — 언제 사는가
```json
"minNetScore": 4,        // signals.ts 순점수. 4 = STRONG_BUY. 낮추면 매매가 늘고 질은 떨어진다
"requireUptrend": true,  // 60일선 위 + 상승 중일 때만. false 로 하면 하락장에서도 물타기 시작한다
"maxOpenPositions": 5,   // 동시 보유 종목 수. 늘리면 분산되지만 종목당 비중이 줄어든다
"cooldownDays": 5        // 청산 후 재진입 금지 일수. 같은 신호로 연속 진입하는 것 방지
```

### exit — 언제 파는가 ★ 수익률을 가장 크게 좌우한다
```json
"stopLossAtrMult": 2,    // 손절 = 진입가 − ATR×2. 이 폭이 1R
"takeProfitAtrMult": 4,  // 익절 = 진입가 + ATR×4  → RR 2:1
"trailingAtrMult": null, // 트레일링 스톱. 3 정도로 켜면 추세를 길게 먹는다
"maxHoldDays": 20,       // 이 봉 수를 넘기면 강제 정리
"exitOnSellVerdict": true // 매도신호가 뜨면 청산
```

**왜 %가 아니라 ATR인가**: 하루 1% 움직이는 종목의 −7%와 하루 5% 움직이는 종목의 −7%는
전혀 다른 사건이다. ATR 배수로 잡아야 변동성이 다른 종목을 같은 규칙으로 다룰 수 있다.

**RR(손익비)** = `takeProfitAtrMult ÷ stopLossAtrMult`. 현재 2:1.
RR 2:1이면 **승률 34%만 넘어도** 기댓값이 양수가 된다. RR을 1:1로 낮추면 승률 50%+비용을 넘겨야 하는데 이건 훨씬 어렵다.

### risk — 얼마를 거는가
```json
"riskPerTradePct": 1,    // 1회 매매에서 잃을 각오를 하는 금액 = 총자산의 1%
"maxPositionPct": 20,    // 한 종목 최대 비중
"dailyLossLimitPct": 3   // 하루 손실이 3% 넘으면 그날 신규 진입 중단
```

**수량은 이렇게 계산된다** (직접 정하는 게 아니다):
```
원금 300만 · 1회 리스크 1% = 3만원
진입가 70,000 · ATR 1,400 → 손절폭 = 1,400 × 2 = 2,800원
수량 = 30,000 ÷ 2,800 = 10주  (진입금액 70만원 = 23% → 비중상한 20%에 걸려 8주로 축소)
```
이렇게 하면 **손절까지 갔을 때 잃는 금액이 항상 3만원으로 고정**된다.
감으로 수량을 정하는 것과의 유일한 차이가 이것이다.

### costs — 거래비용
```json
"commissionBps": 1.5,               // 수수료 0.015%. 증권사 실제 요율로 맞출 것
"slippageBps": 10,                  // 슬리피지 0.1%. 거래량 적은 종목은 20~30으로 올릴 것
"sellTaxBps": { "KR": 15, "US": 0 } // 국내 매도세 0.15%
```
왕복 비용이 약 0.3%. 목표수익 2%짜리 매매면 비용이 수익의 15%를 먹는다.
**매매가 잦을수록 불리하다** — 이게 단타가 어려운 구조적 이유다.

주의할 점:
- **모의용과 실전용은 앱키가 별개다.** 하나로 둘 다 못 쓴다.
- 도메인이 다르다: 모의 `openapivts.koreainvestment.com:29443` / 실전 `openapi.koreainvestment.com:9443`

> `walk-forward.ts` 는 이제 ① 검증 거래 30회 미만 ② 학습 기대값 0.1R 미만이면
> 아예 **판정 불가**로 처리한다.

### 8-6. 진짜 병목은 데이터다

네이버 일봉이 **약 666봉(2.7년)에서 끊긴다** (`--days` 를 늘려도 더 안 온다).
이걸 학습/검증으로 나누면 각 1.3년이고, 진입을 엄격하게 조일수록 표본이 30~60회로 쪼그라든다.
**엄격한 규칙일수록 검증이 불가능해지는 구조다.**

빠져나갈 길은 종목 수뿐이다 — 30종목 → 100종목이면 표본이 3배가 된다.
기간을 못 늘리므로 폭으로 늘려야 한다.

### 8-7. 100종목 × 유니버스 2종 — 처음으로 검증이 성립했다

`walk-forward.ts --universe marketCap,tradingValue --top 100` (합집합 136종목, 64개 중복).

**학습구간 기대값(R) — 같은 후보를 두 유니버스에서:**

| 설정 | 시총 상위 100 | 거래대금 상위 100 | 안정적인가 |
|---|---|---|---|
| 현재 설정 (점수 4) | +0.095 | **+0.102** | ✅ 둘 다 상위 |
| 신호 엄격 (점수 5) | +0.058 | **+0.110** | ✅ 둘 다 양수 |
| 신호 엄격 (점수 6) | +0.092 | +0.092 | ✅ 일치 |
| 신호 엄격 (점수 7) | +0.023 | **-0.047** | ❌ 조이면 나빠진다 |
| 트레일링 스톱 | +0.037 | -0.001 | ❌ 도움 안 됨 |
| 매도신호 무시 | **+0.099** | +0.026 | ⚠ 유니버스 의존 |
| 엄격 + 트레일링 | +0.089 | +0.093 | ✅ 일치 |
| 엄격 + 슬롯 8 | +0.083 | +0.002 | ⚠ 흔들림 |

**검증구간 (승자만, 한 번만):**

| 유니버스 | 승자 | 거래 | PF | 기대값 | 수익률 | MDD | 단순보유 | 판정 |
|---|---|---|---|---|---|---|---|---|
| 시총 상위 100 | 매도신호 무시 | 114 | 1.48 | +0.248R | +25.0% | -9.9~14.7% | +87.1% | ⚪ 판정 불가* |
| 거래대금 상위 100 | 신호 엄격 (점수 5) | 142 | 1.38 | +0.184R | +22.5% | -9.9% | +149.0% | ✅ 유지 (167%) |

\* 학습 기대값 0.099R 이 임계값 0.1R 에 0.001 모자라서. **결과를 보고 임계값을 낮추면 그것도 과최적화다** — 심판을 경기 후에 고치는 것이라 건드리지 않았다.

**얻은 것 세 가지:**

1. **검증 표본 114·142회 — 처음으로 100회를 넘겼다.** 8-5에서 27회로 판정 불가였던 문제가 풀렸다.
   두 유니버스 모두 검증에서 표본·기대값·PF·MDD **4개 기준을 통과**한다.
2. **기본 설정(minNetScore 4)이 이미 거의 최적이다.** 승자와의 기대값 차이가 0.004~0.008R,
   즉 오차 범위다. 튜닝으로 얻을 게 거의 없다는 뜻이고, **과최적화 여지가 적다는 좋은 신호**다.
3. **일관되게 나쁜 방향은 분명하다**: 점수 7로 조이기(❌), 트레일링 켜기(❌).
   8-2에서 "다음에 해볼 것"으로 적어둔 트레일링은 여기서 확실히 기각됐다.

**아직 안 풀린 것:**

- **단순보유를 여전히 못 이긴다** (-62%p, -127%p). 5개 기준 중 이 항목은 계속 ❌다.
- **승자가 유니버스마다 다르다** (매도신호 무시 ↔ 점수 5). 각 승자는 다른 유니버스에선 평범하다.
  어느 설정도 "확실한 우위"가 아니라는 뜻이다.
- **검증구간이 학습구간보다 성적이 좋은 건 규칙이 좋아서가 아닐 수 있다.** 단순보유가
  학습 +81.5% → 검증 +87.1%/+149.0% 로 더 좋았다. 장이 더 친절했던 구간이다.
- **선택 편향은 오히려 커졌다.** 오늘 기준 시총·거래대금 상위 100이라 그 사이 망한 종목이 하나도 없다.

### 8-8. 백테스트는 여기서 멈춘다

백테스트로 얻을 수 있는 것은 대체로 다 얻었다:
표본 100회 이상 확보 ✅ · 워크포워드 통과 ✅ · 설정 민감도 확인 ✅ · 나쁜 방향 기각 ✅.

여기서 더 돌리면 **과최적화만 는다.** 남은 불확실성(단순보유 대비, 유니버스 의존성)은
과거 데이터를 더 파서 풀리는 종류가 아니라 **앞으로의 데이터로만 풀린다.**

→ 다음은 페이퍼 트레이딩이다. `config/stock-trading.json` 은 **그대로 둔다**
(기본 설정과 승자의 차이가 오차 범위이므로 바꿀 근거가 없다).

### 8-9. 미국 규칙을 따로 만들었다 — 방향은 맞았지만 아직 불합격

8-4의 "다음에 시도해볼 것 5번"(미국은 규칙을 따로 만들거나 접는다)을 실행했다.
설정 파일이 **공통 기본값 + `markets.{KR,US}` 덮어쓰기** 2층 구조가 되었고
(`loadTradingConfig("US")`), 백테스트·스윕·워크포워드가 전부 시장을 넘겨 받는다.

미국 규칙은 8-4의 **진단**에서 역산했다 — "일방적 상승장에서 너무 좁게 자르고 너무 일찍 판다":

| 손잡이 | 국내 | 미국 | 왜 |
|---|---|---|---|
| 손절폭 | ATR×2 | **ATR×3** | 휩소에 잘려나가지 않도록 넓힌다 |
| 익절폭 | ATR×4 | **ATR×6** | RR 2:1 을 그대로 유지 |
| 트레일링 | 미사용 | **ATR×3** | 익절선에서 끊지 않고 추세를 태운다 |
| 최대 보유 | 20일 | **40일** | 추세가 길어 20일에 끊으면 상승분을 놓친다 |
| 매도신호 청산 | 예 | **아니오** | 조기 청산의 주범이라 판단 |
| 수수료 | 1.5bp | **7bp** | 미국주식 실제 요율. 구조적 사실이지 튜닝이 아니다 |

**결과** (35종목 · 2023-11 ~ 2026-08 · `--market US`):

| | 국내 규칙 그대로 (8-4) | 미국 전용 규칙 |
|---|---|---|
| 거래 | 306회 | 165회 |
| PF | 0.88 | **1.03** |
| 기대값 | — | +0.042R |
| 총수익률 | **-13.1%** | **+2.0%** |
| MDD | -20.3% | **-11.5%** |
| 단순보유 | +105.9% | +105.9% |

**돈을 잃던 것이 본전 근처로 올라왔다. 그러나 5개 기준 중 3개는 여전히 ❌다**
(기대값 0.042R < 0.1 · PF 1.03 < 1.3 · 단순보유 대비 -103.8%).

남은 병목이 두 개 보인다:

- **비용비중 63.4%** — 손익의 3분의 2가 수수료다. 국내(13.8~41.6%)와 자릿수가 다르다.
  7bp 수수료 아래서 165회를 돌리면 회전 자체가 전략을 잡아먹는다.
- **슬롯참 741회** — 진입 신호는 넘치는데 5슬롯이 계속 차 있다. 미국은 종목이 35개라
  국내(100개)보다 슬롯 경쟁이 심하다.

> **읽는 법**: 진단에서 역산한 규칙이 진단대로 움직였다는 건 8-4의 원인 분석이 맞았다는
> 뜻이다. 하지만 **맞는 방향으로 갔다는 것과 쓸 만하다는 것은 다르다.**
> 국내는 워크포워드까지 통과했지만(8-7) 미국은 아직 스윕도 워크포워드도 안 돌렸다.
> `markets.US.verifiedAt` 이 `null` 인 이유이고, 화면이 "⚠ 검증 전 (가설)" 로 표시하는 이유다.

**미국은 아직 실계좌 후보가 아니다.** 국내가 페이퍼 트레이딩으로 넘어가는 동안
미국은 종이 위에 남는다.

### 8-9. 페이퍼 트레이딩 시작 (2026-08-16 착수 · 2026-08-17 기록 개시)

```bash
# 처음 한 번 — 종목과 규칙을 얼린다
npx tsx ../scripts/paper-trade.ts --market KR --init --universe marketCap --top 100
npx tsx ../scripts/paper-trade.ts --market US --init      # 관심종목을 얼린다

# 그 다음부터 매일
npx tsx ../scripts/paper-trade.ts --market KR
```

| | 국내 | 미국 |
|---|---|---|
| 종목 | 시총 상위 100 (스냅샷) | 관심종목 35 (개별주 23 + ETF 12) |
| 시작일 | 2026-08-17 | 2026-08-17 |
| 진입점수 | 4 | 4 |
| 손절 / 익절 | ATR×2 / ×4 | ATR×3 / ×6 |
| 트레일링 | 없음 | 3 |
| 최대보유 | 20봉 | 40봉 |

**시작일을 8/17로 잡은 이유**: 8/14까지의 데이터는 스윕·워크포워드가 전부 본 것이다.
그 구간을 페이퍼에 포함하면 이미 답을 아는 시험을 다시 치는 셈이라, 진짜 out-of-sample 은
그 다음 거래일부터다. 그래서 **첫 보고서는 비어 있는 게 정상**이다.

**진행 중에는 종목도 규칙도 바꾸지 않는다.** 바꾸는 순간 검증이 아니라 또 한 번의 튜닝이 된다.
바꾸려면 `--init` 으로 새로 시작하고, 그때까지의 기록은 버린다.
그래서 계약서(`config/paper-{market}.json`)를 커밋해 둔다 — 몰래 바뀌지 않게.

**⚠ 이건 KIS 모의계좌가 아니다.** 주문이 어디로도 나가지 않는다 — 네이버 일봉으로
"이 규칙대로면 샀을 것"을 계산해 기록만 하는 순수 시뮬레이션이다.
모의계좌(2단계)는 **실제로 주문을 넣는** 단계이고, 그 주문 코드는 아직 없다
(`lib/stock/kis.ts` 에 주문 함수 자체가 없다 — 조회 전용).
보고서 머리에 그 문구를 박아 둔 이유도 며칠 지나 숫자만 보면 계좌 잔고로 착각하기 쉬워서다.

상시 가동: `.github/workflows/paper-trade.yml` 이 한국장 15:50 KST / 미국장 06:35 KST 에
각각 돌면서 텔레그램으로 보낸다. 매매·보유·후보가 모두 없는 날은 **보내지 않는다** —
매일 "변화 없음" 이 오면 정작 매매가 일어난 날의 알림도 같이 안 읽게 되기 때문이다.

읽는 법:
- **실현 성적**만 성적이다. 보유 중인 종목의 평가손익은 따로 표시되고 성적에 안 섞인다.
- **매수 후보**는 기록이 아니라 예고다. "아직 산 것이 아닙니다" 표시를 지우지 말 것.
- 실현 30회를 넘기기 전 숫자는 읽지 않는다. 4~8주는 지나야 한다.

### 다음에 시도해볼 것

   (8-5 를 보면 답은 이미 "우연" 쪽에 가깝다)
